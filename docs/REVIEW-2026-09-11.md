# Sam: product and engineering review

Reviewed on 11 September 2026. Repository revision: `cef5d8f`.

## Assessment

The intended product is an experienced climbing friend for Alexey and Andrey who learns from ordinary conversation, remembers accurately, and helps them prepare for a shared trip. Low friction, social judgement, and trustworthy memory are the product. Video, analytics, and integrations support that experience.

The current stack is appropriate for this scale. Keep Python, PostgreSQL, and the existing Telegram service. The implementation has useful persistence and analytics foundations, but its central behaviour is still message-by-message extraction followed by a generated answer. Conversation continuity, session continuity, belief revision, and an ongoing coaching cycle need explicit support.

A coherent next release can address these together. The reason to order the work is dependency: coaching and progress reports depend on accurate session records. There is no need to return to seven feature-by-feature product releases.

## 1. One conversation about a session becomes multiple workouts

**Observed:** Andrey's Telegram messages 60 and 61, sent 41 seconds apart on 5 September, describe an unsuccessful 6a attempt followed by three completed easier routes. The database stores these as separate active workouts 5 and 6. The current seven-day analytics therefore count two sessions for that account of a session.

**Cause:** `MessageProcessor._apply_extraction` creates a workout per extracted message unless the entire workout fingerprint matches. Different details produce different fingerprints; there is no session identity or append-to-existing-session action. Extraction also supports only one workout candidate per message, which limits reports covering multiple days.

**Improve:** Resolve each report into a new session, additional details, a correction, or a retrospective summary. Use athlete, event time, reply/thread context, and an explicit session reference where available. Do not blindly merge all workouts on the same day. Keep the supporting messages for every appended fact.

Source: `app/services.py:468`; `app/schemas.py:25`.

## 2. Unknown information still becomes invented precision

**Observed:** Alexey's Telegram message 90 says “Лазил сегодня, болдеринг легкие трассы, минут 40 после работы”. Workout 8 contains one completed climb with grade “легкие трассы”. No count or exact grade was supplied. That invented count appears in current analytics.

**Cause:** `ClimbingEntry.count` defaults to one and cannot be unknown. The evidence check establishes that a quote occurs in the message, not that every extracted field follows from the quote. Analytics also replace missing duration with zero: Andrey's current weekly duration and session load are both zero despite completed climbing activity.

**Improve:** Allow unknown counts; keep descriptions such as “easy” outside the grade field; validate each quantitative field against evidence. Reports should distinguish known volume from unknown volume, and report coverage, such as “40 recorded minutes; duration missing for one session”. A missing effort rating must not become zero training load.

Source: `app/schemas.py:11`; `app/services.py:164`; `app/analytics.py:52` and `:69`.

## 3. Social context is missing, despite storing the group chat

**Observed:** The history contains both unsolicited replies to jokes and missed follow-ups that users repeat with “Сэм”. For example, Telegram messages 34/35 ask the same next-day question; 44/45 repeat a request for further video analysis. Andrey's joke about Alexey's “6c” was interpreted as an expectation for Andrey himself.

**Cause:** Recent context and semantic retrieval filter by the current athlete. The model cannot reliably see both sides of the shared conversation. Reply IDs are stored but the referenced text is not resolved into ordinary text context. Name matching anywhere in a message forces a response, so mentioning Sam in a conversation about him can still trigger him. The last patch removed one backlog bypass, not all causes of bad turn-taking.

**Improve:** Give the conversation decision the actual recent group exchange, named speakers, reply targets, and knowledge of the ongoing exchange with Sam. Keep athlete records separately attributed. A follow-up such as “да, подробнее” should continue the active exchange without repeating the bot's name. Talking about Sam is different from talking to him.

Source: `app/memory.py:136`; `app/services.py:93` and `:298`; `app/telegram.py:416`.

## 4. Correcting a response does not repair the bot's beliefs

**Observed:** Memory 9 remains active for Andrey: “User playfully set 6c as the next target/expectation after prior discussion of current climbing level.” It derives from Telegram message 88, a joke directed at Alexey. Production context currently includes it as a coach memory.

**Correction to the previous assistant report:** The joke did not create a formal event or backlog item, but it did create a memory. The earlier statement that it had not entered memory was incorrect.

**Cause:** Memories are appended. Normal message processing has no general revise/retire-memory operation. Context drops memory confidence, date, status, and source references, presenting only kind and summary. Semantic search includes Sam's own previous replies but returns plain text without speaker or provenance, allowing old mistaken answers to recur as apparent evidence. Correction handling supports only workouts and daily state, although the schema also allows athlete and fact targets.

**Improve:** Give beliefs explicit subjects, evidence, confidence, and revision history. A joke can remain conversational history without becoming a training objective. Propagate corrections to linked memories, profile summaries, facts, and derived statistics. Preserve source identity in every retrieved result and prefer user evidence over Sam's earlier assertions.

Source: `app/services.py:602` and `:739`; `app/memory.py:183` and `:286`.

## 5. Private and shared contexts currently have no visibility boundary

**Code-confirmed risk, not an observed disclosure:** Retrieval filters by athlete, not chat or visibility. A private message can therefore enter the context of a later group response. Conversely, cross-athlete group context is largely absent.

**Improve:** Decide the product policy with the users, then make source visibility part of retrieval and memory. Preserve the shared conversation while restricting private facts to their permitted audience. Privacy cannot depend only on a prompt instruction.

Source: `app/memory.py:141` and `:164`; `app/db/models.py:55`.

## 6. The coaching cycle and dynamic profile are incomplete

**Observed:** Production still has one setup-era plan, owned by Alexey, and one target event also owned by Alexey. Andrey has neither, despite the request that both prepare for the same trip. Alexey's profile still describes the starting climbing baseline. The latest daily state is from 1 September and is still supplied as the latest state.

**Cause:** Most profile attributes cannot be updated through normal extraction. Saved weight measurements are not included by the context builder. Coach-generated plans are recovered from prose using a heuristic and another AI call after the reply is sent. There is no scheduled review, pending-question lifecycle, or process for revising learned patterns. Plans' validity dates are not supplied alongside their contents.

**Improve:** Store a shared trip with individual preparation goals, maintain dated profile facts, and distinguish the baseline from current capability. Make a proposed plan and its structured record one operation, with explicit effective dates and a reason for each revision. Add a modest weekly review and useful follow-ups according to user preferences. Missing training reports must not automatically mean missed workouts. Stale recovery data should be labelled as historical.

Source: `app/services.py:377`, `:571`, and `:678`; `app/memory.py:225` and `:282`; `app/seed.py`.

## 7. Analytics are calculated, but their meanings need work

**Code-confirmed:** French grades do not have a general ranking implementation. Discipline strings are inconsistent in production (`rope`, `route`, `routes`, `bottom_rope`). Highest-grade aggregation does not require successful completion. A best attempted grade can be confused with a best completed grade. Grade conversions in conversation are currently left to the model.

**Improve:** Normalize disciplines and grade systems, preserve original grades and ranges, and separate attempts from completions. Keep rope length or vertical metres when supplied: three 17-metre routes and three very short routes are materially different training evidence. Use a reviewed conversion table with approximate ranges. Explain progress only when the comparison has adequate data coverage and comparable conditions.

The database can hold hundreds of sessions. The immediate problem is correctness and report design, not storage capacity. `render_history_audit` enumerates every workout into one message; an isolated 100-session fixture produced 11,475 characters. Telegram's ordinary sendMessage text limit is 4,096 characters, so long history needs summaries and pagination. See [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

Source: `app/analytics.py:15`, `:63`; `app/memory.py:49`; `app/telegram.py:428`.

## 8. Video feedback can be useful, but current follow-ups add little evidence

**Observed:** Two saved 45-second analyses used 12 frames each. Sam repeatedly offered another level of detail after requests for detail, and addressed the uploaded climber as “you”. The supplied conversation later identifies Andrey as the climber. The runtime has no explicit climber-subject field separate from uploader identity.

**Cause:** Later follow-ups receive the saved textual analysis, not freshly selected video frames. More words do not add visual evidence. Frame labels contain ordinal numbers, not timestamps. Photos/Garmin screenshots and videos sent as document attachments have no dedicated intake path. Bare group video notes are ignored, including any speech they may contain.

**Improve:** Identify whose climbing is shown; support speech intake for video notes independently from an explicit request for visual analysis. For technique, choose one short segment, provide timestamped observations, one practical focus, and clearly stated uncertainty. Reinspect the relevant frames for follow-up questions. Avoid serial “if you want, I can...” offers after the user has already asked for the analysis.

The standard hosted Bot API download limit remains 20 MB. Larger-video handling is a product choice: acceptable compression/short clips, or another upload/download path. See [Telegram getFile](https://core.telegram.org/bots/api#getfile).

Source: `app/video.py`; `app/ai.py:88`; `app/telegram.py:219` and `:236`.

## 9. Runtime recovery is too dependent on manual intervention

**Code-confirmed risks:** An existing message row prevents normal reprocessing even when processing failed. Recovery is a separate manual command for started runs. Processing is marked completed before Telegram delivery; a failed send has no durable pending reply to retry. Voice download occurs before the general processing error handler, and transcription failures return before raw input is persisted. Edited-message updates have no handler. The health endpoint returns HTTP 200 even when the body says degraded and does not probe database availability.

**Reproduced locally:** A synthetic extraction RuntimeError surfaced as SQLAlchemy MissingGreenlet because the exception handler accessed an expired ORM object's ID after rollback. The stored run remained started, and retrying the same input returned duplicate=true with no reply. This provides a concrete explanation for one class of stuck processing; it is not proof that every historical outage had this cause.

**Improve:** Persist incoming updates before media work, process them in order for a conversation, and track received/processing/retryable-failure/completed states. Store outgoing replies durably before delivery and retry them with deduplication. Add explicit handling for edited messages and media failures. Make readiness reflect database and polling health. Keep this inside the existing service and database; a separate queue service is unnecessary at this scale.

Continue daily snapshots, verify a restore, and add an off-platform backup if one is not already maintained. Pin tested dependencies for repeatable builds; the current project specifies version ranges without a lockfile.

The test fixture inherits the live `.env` because it constructs Settings without disabling the env file or overriding the bot token. During the initial test failures, pytest printed that token in the settings representation. Later runs used dummy credentials. Isolate test settings, suppress secret representation, and rotate the exposed Telegram bot token as a coordinated operational change. The token is deliberately not reproduced in this report.

Source: `app/services.py:224` and `:331`; `app/telegram.py:264` and `:428`; `app/recover_pending.py`; `app/main.py:48`; `pyproject.toml`.

## Recommended delivery and acceptance

Build one coherent release, with three internal checkpoints:

1. **Trustworthy observation:** session merging/splitting, unknown values, attribution, corrections, source visibility, and reliable processing. Review and repair existing erroneous records with an audit trail.
2. **Natural conversation:** shared group context, reply resolution, follow-up continuity, selective participation, concise persona, and actionable media feedback.
3. **Useful ongoing coaching:** individual goals for the shared trip, dated plans, factual weekly reviews, and revisable athlete-specific hypotheses.

Create a small evaluation set from the actual failures, including the surrounding conversation. Run the real extraction/coaching path against an isolated database, check expected writes and expected silence, and assess factuality and usefulness of replies. Existing fake-AI unit tests remain useful but cannot establish model behaviour.

Acceptance examples:

- Two messages adding detail to one session create one session; an explicit second session stays separate.
- “40 minutes of easy bouldering” saves duration without inventing a count or grade.
- A joke aimed at Alexey changes neither Andrey's goal nor his coach memories.
- “Да, подробнее” continues Sam's active discussion without an extra invocation.
- Moving the shared trip updates both athletes' relevant plans while preserving individual loads.
- Correcting an attributed workout also corrects related beliefs and derived reports.
- A private disclosure never appears in a group answer unless policy explicitly permits it.
- One hundred sessions produce a readable summary with source-backed drill-down, within delivery limits.
- A temporary API or Telegram delivery failure recovers without silently dropping the workout or duplicating the reply.

Before choosing new integrations, demonstrate one week of ordinary use where both users can report sessions casually, get a correct review, and receive a useful next-step recommendation without debugging the bot themselves.

## Confirmed product decisions — 11 September 2026

Alexey clarified the following after the review:

- Primary value: remember training accurately and help decide what to do next. Progress overviews are part of the core experience.
- Audience: Alexey and Andrey. Success means both actually use Sam for records, advice, and progress reviews.
- Group participation: mostly listen and remember; respond when addressed or when a timely intervention clearly helps.
- Training reports: save them, and ask a useful follow-up when relevant information is missing, for example how the athlete feels. Missing optional fields should not trigger a questionnaire.
- Privacy: training facts may be shared; personal context from private conversations stays private. Store these separately even when supplied in the same message. Group replies must not reveal private context through quotations, explanations, or retrieved summaries. Handling of sensitive or ambiguous facts needs conservative defaults.
- Alexey's goal: improve endurance and become able to lead French 6a+ on rock as part of a multipitch route. This is a target, not an established current ability or a confirmed goal for Andrey.
- Timing: late November is tentative and may move; no exact trip date is known. Preparation should support ongoing progress without assuming a fixed deadline.

These decisions prioritize training memory, useful follow-ups, next-session guidance, and progress reviews ahead of expanding video analysis or adding integrations. They do not authorize a production deployment in this review task.

### Implications for the next release

- A brief workout report and a later answer about fatigue belong to the same session context. Sam should save known facts immediately, ask at most one relevant question at a time, and append the answer without duplicating the workout.
- An unanswered follow-up stays unknown. A missing report is not proof that a workout was skipped.
- Track endurance with available evidence such as route length or vertical metres, completed routes, rest, perceived effort, and recovery. Do not require all of these on every session or invent them when missing.
- Separate bouldering, auto-belay/top-rope, outdoor lead climbing, and multipitch evidence. A gym grade or a single successful pitch does not by itself establish the stated outdoor multipitch capability.
- Compare similar sessions and show data coverage. A progress overview should explain what improved, what is uncertain, and how that informs the next session.
- Keep private personal context out of shared retrieval. If private context informs individual advice, explain that advice privately or use a group-safe explanation that does not expose the context.
- Keep the trip date approximate and editable; retain individual targets and preparation history if the trip moves.

### Remaining discovery

- What grade can Alexey currently lead comfortably outdoors? Previous multipitch experience is confirmed below, but current lead ability remains unverified.
- For the selected 6a+ sections, what would satisfactory performance mean: comfortable leading, or completion with rests/attempts?
- What is Andrey's own target and current baseline? Do not copy Alexey's target to him.
